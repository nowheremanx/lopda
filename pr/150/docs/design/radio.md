# 设计草稿：电波台（内置声波通信）

状态：**M2 已实现，M3 已实现**（2026-10-30，runtime 0.50.0）。会话层和 M4（文本）未做；以后的 app 间通讯见第 7 节。
产品定位：不是 `Acoustic Lab` 调试页，而是一台双机、离线、点对点的“电波台”。`experiments/acoustic-lab` 继续作为调参和回归台。

## 1. 为什么是内置程序

商店 app 跑在 `sandbox="allow-scripts"` 的 iframe 里，源是 opaque origin，浏览器拒绝 `getUserMedia`。
在 iPhone 16 / 13 Pro 上实测是 `NotAllowedError`；只加 `allow="microphone"` 仍然拒绝；加 `allow-same-origin` 能开，
但会破坏商店 app 的隔离。`PAD.mic` 只给 `{level, pitch}`（20 Hz，50–1500 Hz），不够 4-FSK。

内置程序在 runtime 自己的源里运行，可以直接拿原始麦克风、FFT 和 AudioBuffer。因此第一版把声波通信做成内置程序。
商店 app 以后拿到的是**消息级**的 `PAD.link`（第 7 节），不是符号或 PCM：麦克风、配对和重传都归主程序。

## 2. 模块

```
runtime/acoustic.js       纯函数：4-FSK 符号、前导码、合成、同步、已知序列解码
runtime/acoustic-link.js  纯函数：帧、CRC-16、HELLO/DATA/ACK/NACK/FIN
runtime/apps/radio.js     内置“电波台”：麦克风、扬声器、握手、收/发/仪表和日志
tests/acoustic.test.mjs   符号映射、各速率、噪声、静音、截断、定时
tests/acoustic-link.test.mjs  帧、CRC、各类型经过调制解调
```

`acoustic.js` 不碰 DOM 或 Web Audio；它可以在 Node 里直接测。`radio.js` 只做 I/O 和界面。

## 3. M2 的调制与同步

| 项 | 值 |
|---|---|
| 调制 | 4-FSK |
| 音调 | 1500 / 2500 / 3500 / 4500 Hz |
| 符号 | 2 bit；一个字节四个符号，MSB pair 在前 |
| 默认速率 | 10 ms（两台 iPhone 双向都稳；5 ms 视扬声器音量） |
| 前导/同步 | 16 符号：`0 3 0 3 0 3 0 3 1 2 0 3 3 0 2 1` |
| 速率 | 40 / 20 / 10 / 5 ms |
| 发射 | 相位连续的 sine，150 ms 静音前后；一个 AudioBuffer |
| 接收 | 宿主 `getUserMedia`，ScriptProcessor 收 PCM，离线在最后 8 秒搜索同步 |
| 同步 | 1/8 符号网格上的相关，最佳 12/16 后在半/四分之一格内细化 |
| 判决 | 最高/次高 ≥ 6 dB，RMS > −60 dBFS；否则擦除 |
| 解码 | 已知测试序列：符号错误、字节错误、擦除、goodput |
| 帧 | 版本 1、类型、会话 2、序号 2、长度 2、payload、CRC-16 |
| 速率协商 | 10 / 20 / 40 ms 自动握手；5 ms 手动 |
| 可靠传输 | Stop-and-wait，ACK/NACK，3 次 DATA 重试，FIN |

位序示例：`0xB4 = 10 11 01 00 → [2,3,1,0]`。

M2 的接收是“采一段，再解码”，不是持续跟踪。前导码给出起点；一个 burst 内的时钟漂移可以忽略。

## 3.1 M3 握手和可靠链路

- 发送端先用 **10 ms** 发 `HELLO`；接收端在 3.2 秒的采集窗口里同时尝试 10/20/40 ms，解出后用同一速率回
  `HELLO_ACK`。发送端在 10 ms 上等 7 秒；没有 ACK 就改发 20 ms，再 40 ms。这样 HELLO 和 ACK 两个方向都被
  验证过，选出的就是双向都能用的最快档。
- 选定速率后，发送端发一个 `DATA`（M3 用 16 字节测试 payload），接收端校验 CRC 后回 `ACK`；失败回 `NACK`，
  发送端最多重试 3 次。最后 `FIN`/`ACK`。会话 ID 和序号在每一帧里，旧 ACK 不会确认新帧。
- 采集窗口不是死等：每 120 ms 对已收到的样本试解一次，完整 HELLO/ACK/DATA/FIN 一出现就立刻结束窗口、回包或进入下一步；回包前再留 1500 ms 给对端打开麦克风/切回接收；等 ACK 的窗口也相应覆盖这段启动时间（HELLO 最多等 7 秒）。否则发送端会等满 ACK 窗口，接收端已经进入下一个窗口，两边像错开一拍地“自说自话”。
- 半双工：发送 burst 时停麦克风，等 ACK 时停发送。一次链路用同一速率；5 ms 不参与自动握手。
- M3 的接收端在每次 burst 前重新打开麦克风；没有做持续符号时钟，也没有在 ACK 丢失时自动重新握手（M5 的
  退避/重连）。这是当前已知限制。

## 4. 界面

- **发报**：自动握手（M3）或手动测试（M2）；速率/测试序列、十六进制预览、握手/ACK/重试进度。
- **收报**：等待连接（M3）或手动接收（M2）；握手、CRC、ACK、收到与期望的十六进制。
- **仪表**：收到/期望的符号色块、置信度条、日志。
- 自动模式：一台点“等待连接”，另一台点“连接并发送”。手动模式：两台选同样的速率和测试序列，
  先点收报，再点发报。
- 发送时停麦克风；接收时停发送。打开麦克风期间静音键不起作用，状态栏有监听记号。

## 5. 已验证

- `node --test tests/acoustic.test.mjs`：48 kHz 和 44.1 kHz × 40/20/10/5 ms 全部 0 符号错误；噪声、静音、截断、
  定时偏移各有用例。
- 浏览器假麦克风：内置 app 在 40/10/5 ms 都得到 `Sync 16/16`、`0/64` 符号错误、`0/16` 字节错误；
  goodput 分别约 40 / 160 / 320 bit/s。
- M3 帧/CRC：`tests/acoustic-link.test.mjs` 覆盖所有类型、CRC 错误、长度错误，以及 10/20/40 ms 经过
  `acoustic.js` 合成/解码的往返。
- 真机 M2 双机测试（2026-10-29，iPhone 16 + 13 Pro）：
  - 16 → 13 Pro：5 ms 完美。
  - 13 Pro → 16：5 ms 有错，10 ms 完美。
  - 外放、音量足够时 5 ms 可用；确认声音从底部外放出来。提高发射电平（0.55 → 0.9）和强制 `"playback"` 后，结果没有明显变化。
  - 方向差异更像 **接收端**：13 Pro 的话筒能从 16 的 5 ms 信号里正确解码，而 16 接 13 Pro 时需要 10 ms。不是 13 Pro 扬声器的问题。
  - 因此内置 app 默认 10 ms；5 ms 保留给链路很好的一对。
  - 同一套解码器在两个方向结果不同，说明是声学/话筒差异，不是解码逻辑的方向性。

| 层 | 文件 | 做什么 |
|---|---|---|
| 声学 | `acoustic.js` | 4-FSK、前导、同步、判决。不变 |
| 帧 | `acoustic-link.js` | 帧格式和 CRC。帧版本 2 时 HELLO 带端口和协议串，DATA 可捎带 ACK |
| 会话 | `acoustic-session.js`（新，纯函数） | 握手、轮流说话、确认、重传、断线与重连 |

| 程序 | 电波台（第一个用户）、以后的宠物、五子棋…… | 只处理消息 |

**接口定义在消息上，不在声音上。** 以后加别的传输（例如屏幕二维码 → 相机，适合几 KB 的东西），app 一行不改。

### 7.1 会话层

- 纯函数状态机，像 `petsim.js` 一样在 Node 里测：输入“听到一帧 / 发完了 / 时间到”，输出“发这一帧 / 交给上层一条消息 /
  对方丢了”。时钟、麦克风和扬声器由 radio.js（以后是 `LP.link`）注入。
- **双向、长时间**：建立后任何一方都能说话，不是现在的一方发、一方收、FIN 结束。
- **轮流说话**（半双工）：对方的下一帧顺带确认上一帧；空闲时谁先说由发起方决定，两边同时开口时随机退避再说。
- **常听**：等对方落子可能要几分钟。接收只对新到的样本算 Goertzel、缓存结果，搜索窗口有上限；现在每 120 ms 把整段录音
  重搜一遍（`scanHello` 还试三个速率），一次性传输没问题，常听会发烫耗电（推测，要真机测）。
- **只两台**：第一版是点对点，不做多人。
- 帧版本 2 的 HELLO payload：链路协议版本、端口（app id 的短哈希）、app 自己的协议串。端口或协议不同就拒绝，
  界面说“对方在用别的程序”。

### 7.2 `PAD.link` 草案（1.0 之后，不进 lopda/1）

- 权限 `"link"`；配对界面由主程序画（和 `PAD.camera.snap` 的取景器一样），玩家把两台机器凑近、确认，app 只拿到结果。
- 消息级：发一条 ≤ 几百字节的消息、收消息事件、“对方在 / 不在”事件。app 看不到速率、会话号、帧和声音。
- 同一时刻只有一个 app 用链路；离开 app 或锁屏就断，回来可重连，续接由 app 自己按自己的状态做（例如五子棋比步数）。

### 7.3 给以后的场景的约定

- **交换是复制，不是转移**：会丢包的链路上做不到两边同时确定“交换完成”（最后一个确认可能丢）。所以礼物、纪念品发出去后
  送的人也留着（或记一笔“送过”），东西不会凭空消失。
- **串门发的是访客卡片（副本）**：本机宠物的文档永远不被收到的数据改写；收到的内容按 AI 纪念品的标准严格校验。
  宠物走出屏幕的动画就是发送的那几秒，对面在 DATA 解出时让它走进来。
- **加密放在 app 里，不放在链路层**：主程序只搬运密文，这才是端到端。玩具聊天可以用 WebCrypto 的 ECDH 换公钥、AES-GCM
  加密每条消息、两边显示同一个短“安全码”对一下。沙盒 iframe 里 `crypto.subtle` 是否可用、iPhone Safari 是否支持 X25519，
  都还没验证。
- 纸面估算（10 ms 档，未上真机）：五子棋一手 2–4 字节，一来一回约 4–5 秒；宠物访客卡片约 40 字节，一帧约 6 秒；
  中文 50 字约 150 字节、3 帧约 20 秒（40 ms 档约 80 秒），聊天要限长。照片这类几 KB 的东西不走声波。

### 8.2 帧版本 2

```
version(1)=2  type(1)  session(2)  seq(2)  ack(2)  length(1)  payload(length ≤ 60)  crc16(2)
```

- `type` 的低 4 位：HELLO 1、HELLO_ACK 2、DATA 3、ACK 4、BYE 5、PING 6；最高位 `0x80` = 后面还有分片。NACK 去掉：CRC 坏了，头也不可信，靠超时重发。
- `seq`：发送方向自己的序号，每个方向各自从 1 递增；`ack`：我收到的对方最后一个完整序号（捎带确认）。
- 版本 1 的帧一律不认。两台机器都要更新到同一版本 runtime；版本不同就是“听不到对方”，说明页写明。
- HELLO / HELLO_ACK 的 payload：链路协议版本(1)、端口(4，app id 的 FNV-1a，电波台是 `"radio"`)、随机数(2)、
  app 协议串(≤ 16 字节 ASCII，`PAD.link.open({proto})` 给的，默认空)。端口或协议串不同 → HELLO_ACK 带“不同程序”标记，两边都结束并提示。

### 8.3 会话

- **配对是对称的**：两台都按「连线」，谁也不用选“主”或“从”。每台随机听 0.8–2.4 秒，没听到 HELLO 就发一个，然后再听；
  听到 HELLO 的回 HELLO_ACK。发 HELLO 并收到 HELLO_ACK 的一方是**发起方**（五子棋里执黑先走），它再回一个 ACK；应答方收到这个 ACK（或之后任何一帧）才算连上，没收到就重发 HELLO_ACK（最多 5 次）。第一次两台 iPhone 实测，应答方回完 HELLO_ACK 就自己进去了，对方其实没听到（三次握手，owner 2026-11-01）。两台同时发 → 都听不到 → 随机退避再试。
- **速率**：HELLO 先用 10 ms，失败 3 次换 20 ms，再 3 次换 40 ms，然后从头；听的一方三档同时找。HELLO_ACK 用同一档；之后整个会话用这一档。5 ms 不参与。配对 60 秒没成功就放弃。
- **空闲时安静**：没东西要发就不出声。有消息的一方先**听一下**（最近 300 ms 频带里没有能量）再发；对方回 ACK，或者直接回自己的 DATA 捎带确认。
  没等到确认 → 随机退避 0.3–1.2 秒重发，最多 5 次，都失败就是**断线**。
- **心跳**：空闲 25 秒，发起方发一个 PING，对方回 ACK；连续 3 个心跳没回音也算断线。
- **分片**：一条消息 ≤ 200 字节，切成 ≤ 60 字节的 DATA，按序 stop-and-wait，最后一片不带 `0x80`。收齐才交给上层；重复的片再确认、丢弃。
- **离开**：HOME、关掉程序、页面隐藏 → 发一次 BYE（不等确认），本机立刻结束；对方收到 BYE 或超时都结束。
- **回包等待**：麦克风一直开着，不用再等对方重开麦克风；收完一帧后约 1.5 秒回包：iPhone 发声时关着话筒（否则 iOS 走听筒），发完重开话筒要 1–2 秒才稳定（两台 iOS 27 实测），回得太快对方还没在听（真机再调）。

### 8.4 宿主：`LP.link`

- 整个会话一条麦克风流（`getUserMedia`，`echoCancellation/noiseSuppression/autoGainControl` 都关），audio session 一直是
  play-and-record，结束时回到 ambient（和 `PAD.mic` 同样的规矩，decisions.md 第 23 节）。
- **屏蔽自己**：本机播放的时段（按 AudioContext 时间，前 50 ms、后 250 ms）收到的样本直接丢掉，接收器只当这段是静音。
- 发射电平固定（现在的 0.9），不跟掌机音量走，像真的调制解调器；说明页提醒把手机音量调大。
- 配对界面是主程序自己的，盖在程序上（和 `PAD.camera.snap` 的取景器一样）：两台机器的小图、“靠近 10–30 cm，两边都按 A”、
  能听到的握手音、进度、选定的速率；B 取消。连上后关掉，状态栏出一个天线记号（发送时闪）。
- 同一时间只有一个连线。连线期间 `PAD.mic` 返回 `"none"`；`PAD.mic` 开着时 `open` 先停掉它。
- 传输可替换：`link.js` 里一个 `transport` 对象（发字节、收字节）。默认声波；`?linkfake` 用 BroadcastChannel（同一浏览器的两个标签页），
  给 e2e 和开发台用，模拟延迟和丢帧。会话层在两种传输下完全一样。

### 8.5 `PAD.link`（SPEC 6.8）

```js
// "permissions": ["link"]
await PAD.link.open({proto})   // -> "open" | "cancelled" | "denied" | "none" | "busy"；打开主程序的配对界面
PAD.link.send(data)            // data: 字符串或 Uint8Array，编码后 ≤ 200 字节 -> Promise "sent" | "lost" | "closed"
PAD.link.close()
PAD.link.state                 // "closed" | "open"
PAD.link.initiator             // true 表示本机是发起方（只在 open 时有意义）
PAD.on("link", fn)             // fn({type:"message", data}) | fn({type:"close", reason:"bye"|"lost"|"other-app"|"home"})
```

- 第一次 `open` 由主程序的确认框问（和传感器一起记在设置的「传感器与权限」里，可撤销）。
- 排队最多 4 条；满了 `send` 立即返回 `"busy"`。收到的字符串一定是合法 UTF-8；收到什么类型就是发的什么类型。
- app 看不到速率、会话号、帧和声音；加密（如果要）是 app 自己的事。
- `sdk/dev.html`：两个标签页打开同一个 app，就通过 BroadcastChannel 互连；还有一个“回声对端”按钮，单页也能测。
- 检查工具：用了 `PAD.link` 没声明 `"link"` 报错。

### 8.6 电波台改版

### 8.7 五子棋对战（示范）
