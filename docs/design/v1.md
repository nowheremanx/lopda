# 设计草稿：1.0 的范围（基础设施审计）

状态：草稿（2026-10-17），等 owner 逐条勾选。勾完的就是 1.0 的范围，之后一项项实施。

## 目标（owner 2026-10-17）

- 路线：先把基础设施做完整 → 打磨内置程序 → 示范 app 用上每一个接口（也是给开发者的参考）→ 整理文档、仓库和 README（截图、录屏）→ 公开 → 开发者和生态。
- 公开之前先做一次小范围**预览**：只求反馈、不求 PR，顺便找愿意一起维护的人（第 7 节）。

## 1. 1.0 是什么

- **冻结 `lopda/1`**：清单里的接口全部做完、写进 SPEC、有示范 app 之后，宣布规范 1.0。之后 1.0 已有的行为不再改；新接口进 `lopda/2`，用功能检测（`PAD.xxx` 是否存在）兼容。
- 对开发者的承诺："照 1.0 写的 app，以后的掌机上都能跑。"
- runtime 的版本号到时候跳到 1.0.0。

## 2. 新接口（owner 2026-10-17：两个都进 1.0）

`PAD.notes.append` 和 `PAD.say` **已完成**（runtime 0.26.0，decisions.md 第 25 节）。和下面不同的地方：app 只写自己建的笔记（同名的玩家笔记不碰）；
「来自 app」分组只在有 app 笔记时出现；朗读的中文优先选普通话（zh-CN）。

`PAD.camera.snap` **已完成**（runtime 0.28.0，decisions.md 第 28 节）。和下面不同的地方：第一次由主程序的确认框问，同意的记住
（和传感器的授权放在一起，设置里「传感器与权限」可撤销），之后每次都打开取景器、由玩家按快门；取景器打开时显示机身按键；
大小是 `{size: "small" | "large"}`，没有中间尺寸；不加日期。

| 接口 | 权限 | 做什么 | 要点 |
|---|---|---|---|
| `PAD.notes.append(title, text)` | `"notes"` | app 把一段文字写进记事本（按标题找，没有就新建，和 `LP.notes.append` 同一套规则） | 每次调用都由主程序弹确认框，显示 app 名字和要写的文字（截断显示）；A 同意、B 拒绝。写入的笔记记 `src: "app:<id>"`，归进「摘抄」以外的新分组「来自 app」。单次最多 4 KB |
| `PAD.camera.snap(opts)` | `"camera"` | 拍一张照片，返回**四色抖动后**的小图（像素数组，最大 128×112，可选 256×224） | 每次调用打开主程序自己的取景器（和相机同一套，SELECT 换镜头），玩家按快门才拍、按 B 取消。app 永远拿不到原始画面和彩色数据。返回 `{w, h, px}` 或 `null` |
| `PAD.say(text, {lang})`（owner 2026-10-17：进 1.0） | 不需要 | 用系统语音朗读一小段文字 | 复用词典发音的代码；跟随掌机音量，音量 0 时不出声；每秒最多 1 次，单次最多 200 字；离开 app 时停止 |

三个都要：SPEC、检查工具（没声明权限就报错）、开发台模拟（相机用一张生成的测试图）、pad-shim 测试、e2e。

## 3. 整机备份和恢复（owner 2026-10-17：进 1.0，很重要）

**已完成**（runtime 0.25.0，decisions.md 第 24 节）。和下面写的不一样的地方：
`dumpAll()` 的文件字段叫 `value`（`files` 里还有带 typed array 的对象，不只是 Blob）；两个数据库各一个事务（没法合成一个）；
备份里的 backup-meta 记的是这次备份的时间；记事本提醒把整机备份算作导出，但不改写记事本的"上次导出"；
写回旧数据也失败时，提供把旧数据存成备份文件；超过 4 GB（zip 没有 ZIP64）不备份。

公开以后第一个会被问到的问题是"换手机或者清了数据怎么办"。现在记事本、底片、卡带存档各自能导出，但没有一键备份全部。

- **设置 → 备份**：把整台掌机的数据打成一个文件 `lopda-backup-20261017.zip`（用现有的 zip.js），里面是
  - 文档库（`data/users/local/...` 下所有文档）按路径存成 JSON；
  - `LopdaPlatform.files` 里的大文件（潜影 JPEG、导入的词典和书、卡带 ROM 和存档、字体）原样存放；
  - 一个 `manifest.json`：备份格式版本、runtime 版本、时间、每个文件的大小和 CRC。
- **设置 → 恢复**：选一个备份文件，先完整校验，校验通过才动现有数据，然后**整体替换**（按两次确认）。确认框里提供「先备份现在的数据」；恢复过程中在内存里留一份现有数据，写入失败就原样写回，不留下一半新一半旧的状态。不做合并：合并的规则复杂，结果难预测。
- 卡带 ROM 是不是放进备份：默认放（不然恢复后存档对不上卡带）；文件可能很大，备份前显示总大小。
- 社区 app 的存档（`PAD.save`）一起备份。
- 测试：备份 → 清空 → 恢复，所有文档和文件逐字节相同；坏文件、版本太新的文件被拒绝，现有数据不动。

## 4. 第一次打开（已完成，进 1.0）

状态：已完成（runtime 0.27.0）；每个内置程序的首屏均已有操作说明，因此没有新增空状态文案。

新来的人大多在手机上点开链接，头 30 秒决定他留不留。

- 在 iPhone Safari 里打开（不是主屏 app）时，掌机屏幕上显示一张卡片："加到主屏，像真的掌机一样用"，配一句怎么操作（分享 → 添加到主屏幕）。可以关掉，记住不再显示。
- 第一次开机：一个很短的开机画面，然后主屏；不弹任何权限框（传感器、相机都是用到时才问）。
- 检查一遍每个内置程序第一次打开时的空状态：都有一句话告诉玩家能做什么。

## 5. 投稿流程（已完成，进 1.0）

生态卡在"怎么投稿"，而不是 star 数。

| 环节 | 做法 |
|---|---|
| 写 | README 和 CONTRIBUTING 里一段"10 分钟做一个 app"：复制 `sdk/template`，或者把 `sdk/PROMPT.md` 交给 AI |
| 试 | 线上开发台（GitHub Pages 上的 `sdk/dev.html?app=registry/apps/<id>`）直接试，不用装任何东西；写清楚链接 |
| 交 | `.github/PULL_REQUEST_TEMPLATE.md`：投稿检查清单；CI 对改动 `registry/apps/` 的 PR 跑 `check-app.mjs`，失败时用 step summary 和错误标注报告，不发 PR 评论 |
| 审 | `docs/REVIEW.md`：审核标准（原创、许可证、四色、能用按键玩、权限用得合理、音乐来源）。审得快，投稿人也知道会被怎么审 |

状态：已完成（新增 PR 模板、按改动 app 执行的 CI 检查、审核清单和双语快速入门）。

## 7. 预览

- 定位："预览，求反馈"，不是正式发布。
- 反馈先集中在预览的讨论里，不引导去 GitHub 提 issue（仓库先保持安静）。
- 预览前要做到：main 稳定；第 4 节的第一次打开体验；README 至少有一段能看懂的介绍和在线链接。
- 顺便找愿意一起维护仓库的人（审 PR、回 issue）。

## 9. 不进 1.0 的

GPS；app 联网；app 之间直接通信；主屏整理和商店分类（等 app 多到 30 个左右）；lo-game 的倾斜便捷接口（等第二个倾斜游戏）。

## 10. 建议的顺序

1. 第 3 节整机备份（最影响信任）。
2. 第 2 节三个新接口（一个 PR 或者分两个）。
3. 第 5 节投稿流程 + 第 4 节第一次打开（文档和小改动为主，适合 Copilot）。
4. 第 6 节补示范 app。
5. 预览 → 根据反馈修 → 文档和 README → 公开。
